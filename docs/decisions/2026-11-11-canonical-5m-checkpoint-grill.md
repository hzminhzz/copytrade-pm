# ADR: Canonical five-minute position checkpoints (design grill)

**Date:** 2026-11-11
**Status:** OWNER-APPROVED TARGET POLICY (Q1=A; Q2=B; Q3=A; Q4=A; Q5=A; Q6=A; Q7=A; Q8=A). Documentation only, not implemented, merged, deployed, scientifically qualified or trading-authorized.
**Scope:** Shared source-signal interpretation for `copytrade-pm` virtual paper and `prop-production` Guardian. Native REST checkpoint provider authority is approved as a target (Q2=B); collection feasibility, bounded freshness, cross-DEX consistency and financial protocol details remain undecided.
**Related current contract:** [Official selected-position first-known T+300](2026-11-08-position-first-t300.md). That contract and its running services remain unchanged pending a separately authorized, versioned release/cutover.

## Decision

Adopt a new **five-minute position-state sampling policy** as a prospective architecture target. At UTC checkpoint boundaries (00:00, 00:05, 00:10, ...), a single Canonical Wallet Signal Authority (CWSA) compares verified, complete selected-account economic position vectors with the prior admitted checkpoint under its declared scope and policy version. An actionable change produces a shared, durable, proof-carrying target-state signal consumed by all 16 virtual-paper portfolios and the protected Guardian. Unchanged positions do not produce a new trade instruction.

CWSA owns canonical checkpoint/time identity, verified account/scope and position-state interpretation, deduplication and signal provenance. It does **not** own follower financial inventory, broker permission, modeled paper fills, live execution, risk or HALT. Independent paper PM03/PM04 and Guardian retain their respective finance, verification, target application and journals. A shared source checkpoint is not a shared account order or global finance commit.

This **replaces event-triggered first-known T0+300 for the *new policy***; it does **not** preserve five minutes of minimum post-transition delay. A change immediately before a boundary can be acted on soon after that boundary, subject to proof, processing latency, quotes, risk and financial admission. A source round-trip within a five-minute interval may be invisible to the sampled policy. This is a strategy change requiring separately matched costed follower economics and prospective qualification; historical T+300 results are not equivalent.

A canonical checkpoint is not automatically an executable signal. A missing, stale, invalid or incomplete selected-account sample must not be read as a zero/flat position or a valid new-risk opportunity. Restart, reconnect, delayed samples and scope changes must not create retrospective source signals or reset a historical financial action. All **source-driven** increases, reductions, reversals and closes follow the five-minute sampling grid (Q5=A). Independently triggered Guardian risk limits, HALT and emergency protective actions remain active between checkpoints. Held follower inventory is not made flat by a missing sample. Detailed missing-checkpoint recovery and financial intent disposition remain undecided.

## Additional owner-approved Round 2 decisions (2026-11-11)

- **Q3=A — Bounded fresh-as-observed sampling:** At a scheduled UTC five-minute checkpoint, obtain the latest complete, authentic position state within a specified bounded observation/processing window. Record the scheduled boundary, underlying state time if available, actual local receipt, validation and publication separately. A sample obtained at 00:05:04 is not claimed to have been known at 00:05:00. The exact maximum source age and publication grace are **not yet decided**. Missing the window means unavailable, not time-travel recovery.
- **Q4=A — Complete target-state signals:** Publish the full verified desired position vector under the selected account, all declared DEX scope and policy/checkpoint identities, not an executable BUY/SELL delta. Consumers independently derive portfolio targets from frozen signed k and their own account/pod holdings; source state alone does not mint broker permissions. A duplicate target or repeated delivery never itself proves another order is necessary.
- **Q5=A — Source actions only at grid checkpoints:** Source-driven entries, increases, reductions, closes and reversals use the same sampling cadence. Intra-grid source changes may be missed. Guardian/PM03/PM04 independent loss guards and emergency protective actions are not grid-delayed. The later source-exit detection and execution cost are an explicit different economic policy requiring separate scientific and financial qualification.

These choices eliminate consumer-specific source timers but do not eliminate durable consumer effect identities, broker reconciliation, no-blind-retry behavior, source evidence qualification, or native financial risk.

## Q2 provider audit — Vike snapshot API (reviewed; Q2=B approved subsequently)

**Direct provider verification, 2026-11-12:** Vike MCP `hl_market(view=positions, wallet=..., resolution=5m, start=..., end=...)` exposes five-minute historical position rows (48-hour maximum per wallet query); current positions can be wallet-filtered and are paginated by key. `hl_archive(view=datasets)` advertises a `date=latest` positions Parquet (all wallets/assets; sampled provider reply: 419,780 rows, `snapshot_ts=2026-11-11T17:04:00Z`, `generated_at=2026-11-11T17:07:19Z`), replaced around every five minutes. A sampled wallet's past rows ran at minute `:04`, `:09`, `:14`, not exactly UTC `:00`, `:05`, `:10`. The API showed an example wallet with multiple DEXs (HL, IO, XYZ and PARA). These facts make Vike strong for retrospective checkpoint modeling, not automatically an admissible low-latency live checkpoint feed.

**Provider schema caveats:** Vike `snapshot_ts` denotes ingestion write cycle and its `state_ts` typically describes source state **5–10 minutes earlier**. Cycles are irregular, often 5–7 minutes apart; a gap lasts longer. `latest` rows can retain closed positions from an older cycle for up to 15 minutes; only rows at the file's newest snapshot cycle are candidate current rows. Historical days can have missing snapshots and reconstructed hours from fills; archive positions use `Float64` size, not inherently exact native Decimal quantity. A per-wallet positions API that returns open rows alone does not authenticate a complete zero/flat account, all selected DEX coverage, or a coherent common cutoff. Per-row freshness, completeness and correct native precision must be established independently. Vike streams `hl.positions` / `hl.fills` are different event feeds and cannot be treated as full account-position books.

**Q2=B subsequently APPROVED as a future strategy source:** native Hyperliquid complete selected-account REST snapshots at each checkpoint, independently compared with Vike where useful. Unlike official per-account WebSocket subscriptions, REST polling does not consume per-account WS slots; actual rate/budget and all-DEX cross-call coherence still require measurement. Vike remains approved as a future raw-event transport preference, not as independent checkpoint position authority. Rejected now: A = unqualified Vike position snapshots; C = automatic unqualified fallback/hybrid. No source authority or service was changed by this decision.

## Owner-approved Round 3 decisions (2026-11-12)

**Q2=B — Native official REST checkpoint authority.** Under the *new* grid policy, CWSA derives source-of-truth checkpoint books from original authenticated Hyperliquid `clearinghouseState` REST responses for each selected account and every declared selected perp DEX, not from Vike's delayed snapshots or vendor position-change notifications. Each checkpoint must independently establish exact signed quantities, a complete/unchanged selected scope, actual provider/local timestamps, original bytes and provenance, and bounded cross-DEX snapshot coherence. Vike remains a preferred scalable *raw wallet-activity ingestion* transport and an independent historical/diagnostic comparison source; this selection supersedes the **checkpoint truth** portion of the future Vike-first design, not the Vike transport preference. Existing official WS position-first T0+300 stays the installed policy. Native REST feasibility, total IP budget, coherent 14-account/all-DEX collection under load, fresh quotations and exact latency SLO are **not yet verified**; this approval is not live acceptance or cutover.

**Q6=A — Gap and recovery-baseline policy.** A missing, stale, incomplete, mismatched or late scheduled checkpoint has a durable nonactionable outcome and **blocks new source-driven risk** for its affected selected scope. Neither absent rows nor unverified flat create a close. Upon restoration, the first independently verified complete book is a new **recovery baseline**. It cannot originate a new-risk signal even if the last pre-gap position differs. Against independently verified follower inventory, a *proven risk-reducing* convergence toward that restored complete target may be admitted by the financial owner; no new exposure or side flip is authorized from the recovery baseline. New exposure requires a distinct economic position change at a subsequent valid continuous checkpoint under the current source epoch and frozen policy. The follower's unresolved obligations, existing risk and HALT survive the source gap and rebaseline.

**Q7=A — Checkpoint outcome separate from economic signal.** One stable, durable outcome is recorded for each selected account/scope/policy epoch/UTC checkpoint, whether complete changed, complete unchanged, baseline, unavailable or quarantined; each outcome retains provenance and disposition. An ordinary **target-change signal** is produced *only* for a verified economic difference between successive eligible complete observations in uninterrupted scope/continuity. Do not confuse receipt hash/stream cursor, economic-state hash, checkpoint identity and financial effect identity. Duplicates and replays reproduce the same outcome, not new signals. A recovery reduction-only disposition is explicit and must not masquerade as an ordinary new-risk target-change signal.

**Q8=A — Single guarded new-risk opportunity.** Each distinct admissible target-change signal permits **at most one new-risk execution attempt** for each separately frozen paper or Guardian financial consumer/effect. An unchanged checkpoint, duplicate delivery, restart or source replay does **not** retry or 'top up' a previous new-risk attempt merely because the follower is short of the target. Independently reconciled source reductions and account-protective actions remain distinct from this new-risk one-shot rule. Guardian owns pretrade admission, pending orders, reservations, commit-before-send, broker terminality and UNKNOWN outcomes: no blind resubmission, and no new opening order while a conflicting uncertain financial effect remains. Exact opportunity expiry, how a pre-dispatch rejection is disposed, and multi-market/flip execution ordering remain open decisions.

**Decision caveat.** The one-shot rule intentionally sacrifices automatic target chasing after a partial fill or failed entry; this is a specific economic strategy, not exactly-once delivery of remote broker orders. Paper and protected accounts can diverge in actual holdings while sharing the identical source signal identity.

## HyperX Agent API audit — additional candidate, no policy change (2026-11-12)

**Official first-party catalogs:** [Agent API landing page](https://hyperx.trade/hyperliquid/agent-api), [Data API machine-readable catalog](https://data-api.hyperx.trade/api-catalog) and [Copy-Trading API machine-readable catalog](https://api-service.hyperx.trade/api/catalog/copy-trading). These describe two separately authenticated products:

- **Data API** (header `X-API-Key`): wallet analysis `POST /wallet_analysis/{address}` (weight 5), `GET /wallet_metrics/{address}` (weight 2), `GET /fills/{address}` (weight 5), `WS /fills/ws` (weight 5 per message, advertised monitored-address limits free=1, Pro=50, Ultra=300), and discover/aggregate market analytics. These are wallet analytics, fills and market-level aggregates; the catalog **does not** offer a single independently attested, complete, precise all-DEX target state for each selected wallet. Precomputed metrics are not a point-in-time, follower-executable target.
- **Trading API** (header `x-hyperx-trading-token`, **not** the Data API key) documents `POST /api/hyperliquid/allDexsClearinghouseState` with body `{user, is_testnet?}`: purported per-DEX position breakdown for a wallet in one request. `POST /api/hyperliquid/clearinghouseState` merges DEX positions by default and returns margin/position data. The first endpoint might substantially reduce client-side multi-DEX polling and provide useful comparison evidence, **if** it returns the entire selected per-DEX census and a coherent, sufficiently current state. Its live 14-account/all-DEX completeness, exact source timestamps, native original-byte provenance, precision, rate limits, and availability are **unverified**. No proof that it is a native atomic snapshot has been established.
- **Trading token risk:** the same broad, persistent token permits copy-trading configuration changes, order placement/close/cancel/leverage and other wallet operations. It is **not** a read-only account-state credential. Never provision it to CWSA or a read-only source collector merely to reduce REST calls. Any future isolated read-only comparison must prove separately scoped permission/credential boundaries without creating a new financial authority.
- **Built-in HyperX copy trading:** supports `follow_increase`, `follow_decrease`, `copy_current_position`, `fundingRatio`/`fixedAmount`/`positionRatio` sizing, margin/leverage caps and testnet. These are vendor-controlled follower actions, **not** our UTC five-minute state-target reconciliation, frozen `source-notional fixed-k`, one-shot changed-checkpoint IDs, 16-paper ledgers or Guardian financial conservation/authorization. Do not wire its copy-trading/Trading API mutations into the proposed Propr/Bybit Guardian lane.
- **VPS inspection:** an existing owner-private HyperX **Data API** key is present (not published). A single read-only `wallet_analysis` probe returned HTTP 403; a separate unauthenticated `GET /api-catalog` from that same VPS also returned HTTP 403. Therefore the observation does **not** show that the key is invalid or that authenticated HyperX position reads work. No trading token was loaded, output, created or used; no mutation endpoints were called.

**Disposition:** **ADOPT** existing Data API as optional nonauthoritative research/discovery source where accessible; **EXPERIMENT** with one-call all-DEX *read-only* comparison only after safe least-privilege authentication and original-native validation can be demonstrated; **IGNORE** vendor copy-trading as a substitute for CWSA or Guardian. **Q2=B remains binding for the approved target**: CWSA uses complete native Hyperliquid REST positions for source truth; HyperX and Vike cannot confer authoritative completeness by declaration. Preserve existing current T0+300 installed behavior.

## Why this abstraction

The existing source-to-paper path schedules per-observed-transition T+300; `prop-production.v4_timing.V4ShadowProjection` separately schedules market-level T+300 eligibility. These implementations can diverge on local first-known time, coalescing and recovery. One checkpoint-state authority removes the *need for duplicated source timing*, not the need for independent Guardian verification and durable uncertain-broker-outcome recovery.

The alternative rejected for this *new policy* is to keep independent first-transition clocks for each consumer. The existing T+300 system remains a supported historical/current version until deliberately retired through a new contract and reversible release.

## Explicitly unresolved: next design frontier

- **Settled Q3:** UTC checkpoint identity plus bounded, actually verified source observation time; **unsettled:** numerical freshness/grace limits, cross-DEX consistency and late-sample discard rules.
- **Settled Q6:** failed checkpoints fence new risk; restoration forms nonactionable baseline with independently verified reduction-only policy; **unsettled:** exact late-sample, baseline identity and cross-DEX coherence tests.
- **Settled Q7:** durable checkpoint outcomes separate from economic change signals; **unsettled:** exact signed proof schema, scope/epoch/sequence and consumer hash binding.
- **Settled Q4/Q5/Q8:** complete target-state signal, grid-timed source changes and one-shot new-risk attempts; **unsettled:** pre-dispatch-block disposition, expiry, flip/partial-fill semantics and broker outcome recovery.
- **Settled Q2=B target:** native Hyperliquid REST source authority; **unsettled:** measured 14-account/all-DEX rate budget, provenance, collection skew, completeness and runtime proof.
- Financial proof and release cutover: Guardian verifies signatures, complete scope, market/account finance and signed k; no execution permit from a source signal.

## Safety and migration constraints

No code, service, wire, source/financial journal, existing policy, signed release, tests or authorization is changed by this ADR. Do not reinterpret v1/v2 source receipts or old financial events under the new strategy; use a new policy/wire identity and explicit forward-only cutover. No retroactive alpha claim from historical fill timestamps. Missing external provider proof continues to block affected actions.
