# ADR: Canonical five-minute position checkpoints (design grill)

**Date:** 2026-11-11
**Status:** OWNER-APPROVED TARGET POLICY (Q1–Q24; Q2=B, Q13=B, all other Q=A), with explicit domain-owned transition contract. Documentation only, not implemented, merged, deployed, scientifically qualified or trading-authorized.
**Scope:** Shared source-signal interpretation for `copytrade-pm` virtual paper and `prop-production` Guardian. Native REST checkpoint provider authority is approved as a target (Q2=B); collection feasibility, bounded freshness, cross-DEX consistency and financial protocol details remain undecided.
**Related historical contract:** [Official selected-position first-known T+300](2026-11-08-position-first-t300.md). Owner retired V4 as an operational source policy on 2026-11-14, ahead of ANOS real-data E2E. This does not activate paper finance or protected trading; preserved original V4 receipts remain historical-only.

## Decision

Adopt a new **five-minute position-state sampling policy** as a prospective architecture target. At UTC checkpoint boundaries (00:00, 00:05, 00:10, ...), a single Canonical Wallet Signal Authority (CWSA) compares verified, complete selected-account economic position vectors with the prior admitted checkpoint under its declared scope and policy version. An actionable change produces a shared, durable, proof-carrying target-state signal consumed by all 16 virtual-paper portfolios and the protected Guardian. Unchanged positions do not produce a new trade instruction.

CWSA owns canonical checkpoint/time identity, verified account/scope and position-state interpretation, deduplication and signal provenance. It does **not** own follower financial inventory, broker permission, modeled paper fills, live execution, risk or HALT. Independent paper PM03/PM04 and Guardian retain their respective finance, verification, target application and journals. A shared source checkpoint is not a shared account order or global finance commit.

This **replaces event-triggered first-known T0+300 for the *new policy***; it does **not** preserve five minutes of minimum post-transition delay. A change immediately before a boundary can be acted on soon after that boundary, subject to proof, processing latency, quotes, risk and financial admission. A source round-trip within a five-minute interval may be invisible to the sampled policy. This is a strategy change requiring separately matched costed follower economics and prospective qualification; historical T+300 results are not equivalent.

A canonical checkpoint is not automatically an executable signal. A missing, stale, invalid or incomplete selected-account sample must not be read as a zero/flat position or a valid new-risk opportunity. Restart, reconnect, delayed samples and scope changes must not create retrospective source signals or reset a historical financial action. All **source-driven** increases, reductions, reversals and closes follow the five-minute sampling grid (Q5=A). Independently triggered Guardian risk limits, HALT and emergency protective actions remain active between checkpoints. Held follower inventory is not made flat by a missing sample. Recovery-baseline behavior is decided (Q6=A); the subsequent Q19/Q22 decisions settle unknown-order ownership and opportunity expiry. Numerical freshness limits and native provider proof remain unverified.

## Additional owner-approved Round 2 decisions (2026-11-11)

- **Q3=A — Bounded fresh-as-observed sampling:** At a scheduled UTC five-minute checkpoint, obtain the latest complete, authentic position state within a specified bounded observation/processing window. Record the scheduled boundary, underlying state time if available, actual local receipt, validation and publication separately. A sample obtained at 00:05:04 is not claimed to have been known at 00:05:00. The exact maximum source age and publication grace are **not yet decided**. Missing the window means unavailable, not time-travel recovery.
- **Q4=A — Complete target-state signals:** Publish the full verified desired position vector under the selected account, all declared DEX scope and policy/checkpoint identities, not an executable BUY/SELL delta. Consumers independently derive portfolio targets from frozen signed k and their own account/pod holdings; source state alone does not mint broker permissions. A duplicate target or repeated delivery never itself proves another order is necessary.
- **Q5=A — Source actions only at grid checkpoints:** Source-driven entries, increases, reductions, closes and reversals use the same sampling cadence. Intra-grid source changes may be missed. Guardian/PM03/PM04 independent loss guards and emergency protective actions are not grid-delayed. The later source-exit detection and execution cost are an explicit different economic policy requiring separate scientific and financial qualification.

These choices eliminate consumer-specific source timers but do not eliminate durable consumer effect identities, broker reconciliation, no-blind-retry behavior, source evidence qualification, or native financial risk.

## Q2 provider audit — Vike snapshot API (reviewed; Q2=B approved subsequently)

**Direct provider verification, 2026-11-12:** Vike MCP `hl_market(view=positions, wallet=..., resolution=5m, start=..., end=...)` exposes five-minute historical position rows (48-hour maximum per wallet query); current positions can be wallet-filtered and are paginated by key. `hl_archive(view=datasets)` advertises a `date=latest` positions Parquet (all wallets/assets; sampled provider reply: 419,780 rows, `snapshot_ts=2026-11-11T17:04:00Z`, `generated_at=2026-11-11T17:07:19Z`), replaced around every five minutes. A sampled wallet's past rows ran at minute `:04`, `:09`, `:14`, not exactly UTC `:00`, `:05`, `:10`. The API showed an example wallet with multiple DEXs (HL, IO, XYZ and PARA). These facts make Vike strong for retrospective checkpoint modeling, not automatically an admissible low-latency live checkpoint feed.

**Provider schema caveats:** Vike `snapshot_ts` denotes ingestion write cycle and its `state_ts` typically describes source state **5–10 minutes earlier**. Cycles are irregular, often 5–7 minutes apart; a gap lasts longer. `latest` rows can retain closed positions from an older cycle for up to 15 minutes; only rows at the file's newest snapshot cycle are candidate current rows. Historical days can have missing snapshots and reconstructed hours from fills; archive positions use `Float64` size, not inherently exact native Decimal quantity. A per-wallet positions API that returns open rows alone does not authenticate a complete zero/flat account, all selected DEX coverage, or a coherent common cutoff. Per-row freshness, completeness and correct native precision must be established independently. Vike streams `hl.positions` / `hl.fills` are different event feeds and cannot be treated as full account-position books.

**Q2=B subsequently APPROVED as a future strategy source:** native Hyperliquid complete selected-account REST snapshots at each checkpoint, independently compared with Vike where useful. Unlike official per-account WebSocket subscriptions, REST polling does not consume per-account WS slots; actual rate/budget and all-DEX cross-call coherence still require measurement. Vike remains approved as a future raw-event transport preference, not as independent checkpoint position authority. Rejected now: A = unqualified Vike position snapshots; C = automatic unqualified fallback/hybrid. No source authority or service was changed by this decision.

## Owner-approved Round 3 decisions (2026-11-12)

**Q2=B — Native official REST checkpoint authority.** Under the *new* grid policy, CWSA derives source-of-truth checkpoint books from original authenticated Hyperliquid `clearinghouseState` REST responses for each selected account and every declared selected perp DEX, not from Vike's delayed snapshots or vendor position-change notifications. Each checkpoint must independently establish exact signed quantities, a complete/unchanged selected scope, actual provider/local timestamps, original bytes and provenance, and bounded cross-DEX snapshot coherence. Vike remains a preferred scalable *raw wallet-activity ingestion* transport and an independent historical/diagnostic comparison source; this selection supersedes the **checkpoint truth** portion of the future Vike-first design, not the Vike transport preference. Existing official WS position-first T0+300 stays the installed policy. Native REST feasibility, total IP budget, coherent 14-account/all-DEX collection under load, fresh quotations and exact latency SLO are **not yet verified**; this approval is not live acceptance or cutover.

**Q6=A — Gap and recovery-baseline policy.** A missing, stale, incomplete, mismatched or late scheduled checkpoint has a durable nonactionable outcome and **blocks new source-driven risk** for its affected selected scope. Neither absent rows nor unverified flat create a close. Upon restoration, the first independently verified complete book is a new **recovery baseline**. It cannot originate a new-risk signal even if the last pre-gap position differs. Against independently verified follower inventory, a *proven risk-reducing* convergence toward that restored complete target may be admitted by the financial owner; no new exposure or side flip is authorized from the recovery baseline. New exposure requires a distinct economic position change at a subsequent valid continuous checkpoint under the current source epoch and frozen policy. The follower's unresolved obligations, existing risk and HALT survive the source gap and rebaseline.

**Q7=A — Checkpoint outcome separate from economic signal.** One stable, durable outcome is recorded for each selected account/scope/policy epoch/UTC checkpoint, whether complete changed, complete unchanged, baseline, unavailable or quarantined; each outcome retains provenance and disposition. An ordinary **target-change signal** is produced *only* for a verified economic difference between successive eligible complete observations in uninterrupted scope/continuity. Do not confuse receipt hash/stream cursor, economic-state hash, checkpoint identity and financial effect identity. Duplicates and replays reproduce the same outcome, not new signals. A recovery reduction-only disposition is explicit and must not masquerade as an ordinary new-risk target-change signal.

**Q8=A — Single guarded new-risk opportunity.** Each distinct admissible target-change signal permits **at most one new-risk execution attempt** for each separately frozen paper or Guardian financial consumer/effect. An unchanged checkpoint, duplicate delivery, restart or source replay does **not** retry or 'top up' a previous new-risk attempt merely because the follower is short of the target. Independently reconciled source reductions and account-protective actions remain distinct from this new-risk one-shot rule. Guardian owns pretrade admission, pending orders, reservations, commit-before-send, broker terminality and UNKNOWN outcomes: no blind resubmission, and no new opening order while a conflicting uncertain financial effect remains. Exact opportunity expiry, how a pre-dispatch rejection is disposed, and multi-market/flip execution ordering remain open decisions.

**Decision caveat.** The one-shot rule intentionally sacrifices automatic target chasing after a partial fill or failed entry; this is a specific economic strategy, not exactly-once delivery of remote broker orders. Paper and protected accounts can diverge in actual holdings while sharing the identical source signal identity.

## HyperX Agent API audit — additional candidate, no policy change (2026-11-12)

**Official first-party catalogs:** [Agent API landing page](https://hyperx.trade/hyperliquid/agent-api), [Data API machine-readable catalog](https://data-api.hyperx.trade/api-catalog) and [Copy-Trading API machine-readable catalog](https://api-service.hyperx.trade/api/catalog/copy-trading). These describe two separately authenticated products:

- **Data API** (header `X-API-Key`): wallet analysis `POST /wallet_analysis/{address}` (weight 5), `GET /wallet_metrics/{address}` (weight 2), `GET /fills/{address}` (weight 5), `WS /fills/ws` (weight 5 per message, advertised monitored-address limits free=1, Pro=50, Ultra=300), and discover/aggregate market analytics. These are wallet analytics, fills and market-level aggregates; the catalog **does not** offer a single independently attested, complete, precise all-DEX target state for each selected wallet. Precomputed metrics are not a point-in-time, follower-executable target.
- **Trading API** (header `x-hyperx-trading-token`, **not** the Data API key) documents `POST /api/hyperliquid/allDexsClearinghouseState` with body `{user, is_testnet?}`: purported per-DEX position breakdown for a wallet in one request. `POST /api/hyperliquid/clearinghouseState` merges DEX positions by default and returns margin/position data. The first endpoint might substantially reduce client-side multi-DEX polling and provide useful comparison evidence, **if** it returns the entire selected per-DEX census and a coherent, sufficiently current state. Its live 14-account/all-DEX completeness, exact source timestamps, native original-byte provenance, precision, rate limits, and availability are **unverified**. No proof that it is a native atomic snapshot has been established.
- **Trading token risk:** the same broad, persistent token permits copy-trading configuration changes, order placement/close/cancel/leverage and other wallet operations. It is **not** a read-only account-state credential. Never provision it to CWSA or a read-only source collector merely to reduce REST calls. Any future isolated read-only comparison must prove separately scoped permission/credential boundaries without creating a new financial authority.
- **Built-in HyperX copy trading:** supports `follow_increase`, `follow_decrease`, `copy_current_position`, `fundingRatio`/`fixedAmount`/`positionRatio` sizing, margin/leverage caps and testnet. These are vendor-controlled follower actions, **not** our UTC five-minute state-target reconciliation, frozen `source-notional fixed-k`, one-shot changed-checkpoint IDs, 16-paper ledgers or Guardian financial conservation/authorization. Do not wire its copy-trading/Trading API mutations into the proposed Propr/Bybit Guardian lane.
- **VPS inspection:** an existing owner-private HyperX **Data API** key is present (not published). A single read-only `wallet_analysis` probe returned HTTP 403; a separate unauthenticated `GET /api-catalog` from that same VPS also returned HTTP 403. Therefore the observation does **not** show that the key is invalid or that authenticated HyperX position reads work. No trading token was loaded, output, created or used; no mutation endpoints were called.

**Disposition:** **ADOPT** existing Data API as optional nonauthoritative research/discovery source where accessible; **EXPERIMENT** with one-call all-DEX *read-only* comparison only after safe least-privilege authentication and original-native validation can be demonstrated; **IGNORE** vendor copy-trading as a substitute for CWSA or Guardian. **Q2=B remains binding for the approved target**: CWSA uses complete native Hyperliquid REST positions for source truth; HyperX and Vike cannot confer authoritative completeness by declaration. Preserve existing current T0+300 installed behavior.

## HyperX copy-wallet architecture lessons — revised Round 4 context (nonbinding analysis)

**Source-derived public contract, not an audit of HyperX's private engine:** [official Copy-Trading API catalog](https://api-service.hyperx.trade/api/catalog/copy-trading), [HyperX wallet setup guide](https://hyperx.trade/hyperliquid/blog/hyperx-copy-trading-wallet-setup-guide), and [Copy Trading tutorial](https://hyperx-1.gitbook.io/hyperx-docs/tutorial/copy-trading).

- **Distinct relationship identity:** `copy-trading/create` binds `copy_wallet_address` (leader) to `wallet_address` (follower) with a configuration ID, `is_active`, a sizing mode, filters and limits. The API forbids editing either wallet address in-place (delete/recreate instead); these represent a distinct policy relationship, **not** the global leader position feed. In this project, a signed `portfolio_release_v1.members[]` already holds `source_identity`, `pod_id`, account scope, `k` and allowed markets. The better abstraction is to deepen that existing signed *copy mandate*, not build a second source clock or configuration service.
- **Bootstrap is a policy decision:** HyperX exposes `copy_current_position` on create. A leader already long when the follow relationship starts is different from the first genuine post-activation change; our current design has a nonactionable initial baseline. Whether an initial copy is allowed is a *new economic policy*, not a source-observation bug.
- **Missed-entry response is a policy decision:** `follow_increase`, `follow_decrease`, and especially `copy_increase_as_open_position` distinguish a new master position, an increase to one already followed, and a later master increase after a follower missed the original entry. With complete target-state signals, a new source increase can otherwise silently pull an unfilled follower all the way to the full new target. The rule needs explicit signed economics and must respect previously approved one guarded attempt per changed checkpoint.
- **Stopping is not flattening:** The API documents copy-configuration DELETE as *soft-delete*, stopping future copying while preserving existing positions. Pausing, winding down and an explicit authorized flatten must therefore be distinct from loss protection and source signal validity in our protected Guardian. A different HyperX wallet force-delete UI behavior is **not** the same operation.
- **Per-copy guardrails are not source truth:** HyperX supports `fundingRatio`, `fixedAmount`, `positionRatio` and leverage, margin, TP/SL, asset and copy-action filters. We retain frozen source-notional `k` and account/pod-level safety limits rather than vendor sizing semantics. A dedicated follower wallet may isolate risk in HyperX; our shared prop account instead requires independent pod attribution plus net broker orders.
- **Failure classification before retry:** The catalog distinguishes missing master/follower positions, insufficient follower balance, below-minimum order, source/follower state API failure, rate limiting, exchange/order error and unknown errors. Its public order-placement request does **not document** a caller idempotency key or a full causal broker reconciliation protocol. That omission is not proof that HyperX's private engine lacks these. Guardian must separate *no broker dispatch happened* from *broker dispatch may have happened*; never blindly retry a potentially executed order.

**Not established by public sources:** HyperX's actual internal worker topology, atomicity of native polling, source/event dedup keys, database transaction order, restart semantics, client order IDs, financial risk conservation or measured tail latency. Its landing-page `INIT/SYNC/WATCH/SIGNAL/CALC/EXEC/FILL` sequence is a product demonstration, not independently verified source code or reliability evidence.

**Original design questions, resolved in the subsequently approved Round 4 below:** Q9 freshness, Q10 DEX completeness, Q11 netting, Q12 source-and-mandate proof, Q13 bounded pre-dispatch checks, Q14 activation baseline, Q15 new source increase following a missed entry, and Q16 pause versus flatten. Comparative product evidence alone did not authorize implementation; the owner later approved the specific policies below.

## Owner-approved Round 4 decisions (2026-11-12)

**Q9=A — evidence-qualified checkpoint freshness.** A scheduled UTC five-minute checkpoint is admissible only if native evidence for **every selected account/DEX component** satisfies a separately versioned upper bound on underlying state age, local acquisition duration, response skew across DEXs, and source-receipt publication grace. Preserve source/state, request, first-local-receipt, checkpoint and financial-decision clocks independently. Limits must be *chosen from measured worst-case/load evidence before activation* and frozen as policy; none are assumed by this ADR. A time-out is recorded as unavailable, never backfilled into an earlier actionable checkpoint.

**Q10=A — complete selected-account census, including verified empty.** Source position truth requires explicit native response and parseable selected-DEX/account identity for every scope member. An authenticated/native empty `assetPositions` response is proof of flat **only for that explicitly returned DEX at that observed time**; absence of a wallet or missing pagination/DEX response is not proof of zero. Reject whole-account new-risk admission on partial DEX collection. Record exact DEX/instrument identity (HIP-3 names included), scope generation, signed Decimal quantities and provenance; do not silently merge incomplete evidence or treat unavailable as close.

**Q11=A — pod-independent finance, guarded net execution.** Each copy mandate/pod independently computes frozen-k desired exposure, account/risk constraints and attributed financial consequences from the same canonical source checkpoint. For a shared destination account, Guardian aggregates eligible pod deltas per instrument into **at most one net broker order for that checkpoint where safely representable**. Independent pod exposure/risk budgets, zero-net internal attribution, partial fills, commissions, rejected legs and pending broker effects remain explicit; netting must not manufacture internal P&L or cancel pod obligations. Unresolved orders, incompatible exposures, unverified source changes and dangerous reversals block unsafe opens. One order is a preference subject to native broker invariants, not permission to split execution across many delayed entries.

**Q12=A — source proof + signed copy mandate, two authorities.** CWSA signs a versioned checkpoint outcome or changed target with policy epoch, selected source account/DEX scope generation, UTC boundary, original native REST body hashes, actual source/receipt/acquisition clocks, complete economic vector, source sequence and predecessor identity. Guardian independently checks the proof and links it to **its own** signed account-bound copy mandate/release (source-to-pod mapping, frozen k, allowed assets, timing/entry/exit/activation policy) and independently acquired financial/market evidence. Source signatures prove CWSA's receipt claims, **not** an exchange cryptographic signature or a broker permit. No separate mandate service or alternative source scheduler is created. New wire/release versions are required; existing `source_book_v1` and `portfolio_release_v1` semantics remain immutable.

**Q13=B — bounded pre-dispatch re-evaluation, no blind retry.** Within the **same** source change opportunity and original expiry window, a transient *pre-dispatch* blockage may be re-evaluated with fresh independent risk, quotes, broker account and signed release evidence **only when it is provable that no order reached the broker**. A risk/permission/HALT failure is never bypassed, and a terminal policy rejection cannot be converted into a trade by a mutable local flag. The first irreversibly committed/possibly dispatched new-risk intent consumes the single allowed attempt; a broker timeout/unknown cannot be resent as a new order. A missed deadline is a terminal missed opportunity. Re-evaluation does not reset checkpoint time, release floor, or proof chain; unchanged checkpoints cannot retry.

**Q14=A — activation is a nonactionable baseline.** Enabling a new leader-to-pod copy mandate or materially changing its binding/scope starts a distinct **copy-mandate policy generation** with an independently verified complete first checkpoint; the already-shared CWSA source-scope epoch is unchanged unless its own source/account/DEX scope actually changes. Pre-existing leader positions are **observed** but not automatically copied. No `copy_current_position` behavior exists by default and a new signed release cannot retroactively invent a source change. Historical portfolio starts and running T+300 receipts retain their original meanings.

**Q15=A — new leader increase may open after missed initial entry.** After a previously missed/blocked source opening, a **subsequent valid, independently changed** leader increase in the same supported instrument creates its *own* new-risk opportunity toward the **full current** policy-scaled leader target, based on actual reconciled follower holdings, not merely the incremental source change. It remains subject to frozen k, allowed market, source continuity, fresh marks, unique effect ID and all financial risk caps. A repeated unchanged target does nothing; this new opportunity never clears unresolved broker orders or bypasses a financial HALT. Choosing full current target may enter late, so its economics require separately matched evaluation.

**Q16=A — pause/retire separate from flatten.** Pausing or retiring a copy mandate stops new source-driven exposure and new opening attempts immediately for that mandate while maintaining independent Guardian responsibility for already-held pod/follower exposure, pending/unknown orders, financial HALT and risk-reducing exits. A deliberate **flatten all** is a separate, explicitly authorized account-bound financial action with independent price/risk/terminal-outcome evidence. Disabling a source feed or deleting a relationship **never** means positions are flat. Renewing/re-enabling after material changes uses a prospective, nonactionable activation baseline and new policy epoch; do not reinterpret historical source signals.

## Owner-approved Round 5 — scope isolation, policy succession, finance uncertainty, qualification (2026-11-12)

**Q17=A — failure isolation under shared portfolio finance.** Every selected source account/scope has its own independently checked checkpoint-continuity authority. If source B has any required missing/invalid DEX, B is not a complete source and produces no new-risk signal; independently valid A and C remain eligible for their own signals **only** when shared portfolio and destination-account limits, data dependencies and Guardian/Paper authority independently allow them. A shared signer compromise, destination broker/account uncertainty or other genuinely shared dependency fences *every affected consumer*, not just the first failing wallet. A portfolio evaluation missing B's valid opportunities is **incomplete economic evidence**, not a clean comparison or B=flat. No global 16-portfolio readiness flag can grant or veto unrelated capabilities.

**Q18=A — signed mandate revision and prospective succession.** A material change in leader identity, selected scope, allowed assets, frozen `k`, timing, risk or activation/reduction rules creates a new signed **copy mandate generation** and prospective baseline, not an in-place edit. Preserve old signed releases, source/financial evidence, account positions, pod attribution, HALTs, reservations and outstanding broker effects. One opening-effective mandate generation per destination account/pod relationship at a time; retiring one generation does not erase its residual financial liabilities. **Critical ownership distinction:** changing only one follower's mandate MUST NOT reset the common CWSA source-scope epoch or its checkpoints for other followers. A CWSA source epoch changes only for genuine changes to the source-account/scope authority; mandate epochs are destination-specific.

**Q19=A — unknown native execution is outstanding risk, not a failed order.** An order committed for possible dispatch retains its original financial effect ID, conservative reservation and all observed partial fills until independent account-bound broker status/history/execution reconciliation proves terminality and financial conservation. Block conflicting opening risk across every affected pod/account; do not blindly resend, cancel by assumption, clear HALT, or use a future unchanged checkpoint to create another opportunity. A separately proven protective reduction may be evaluated by Guardian, but the source checkpoint never owns it. Failed broker connectivity does not erase follower inventory.

**Q20=A — independent acceptance gates.** Evaluate four independent capabilities: (1) engineering tests/proof and replay compatibility; (2) authentic 14-selected-account/all-required-DEX REST completeness, skew/freshness, latency and operational resource behavior; (3) separately recorded **prospective, actual/costed** matched follower economics against the old event-driven T0+300 baseline, including delayed source exits, missed openings/full-target later increases, netting and drawdown; and (4) account-bound financial reconciliation, signed release, protected broker permission and explicit owner authorization. Historical hindsight, passing tests, Shadow source collection and paper evidence cannot substitute for live broker authorization or prove trading edge. Read-only evidence collection is not blocked by unrelated live-science readiness.

### Abstraction rule: explicit domain transitions, no hidden state machines (owner instruction)

Reuse the existing [domain-owned proof-carrying transition contract](2026-11-11-invariant-grill-design-closure.md), not a new approval service, distributed transaction, central state machine or `is_ready` boolean pile. Three bounded authorities own the minimum state they need:

| Existing owner / aggregate | Explicit contractual lifecycle (future policy; precise wire symbols pending) | Legal cause of advance | Durable result |
| --- | --- | --- | --- |
| **CWSA source-scope continuity** | UNANCHORED → CONTINUOUS ↔ FENCED | Verified *initial* baseline → continuous unchanged/changed complete checkpoints; a gap invalidates continuity; verified first complete recovery returns to continuous **as nonactionable recovery baseline** | One checkpoint outcome each boundary; separate change signal only for genuine economic change between successive eligible complete checkpoints |
| **Signed copy mandate generation** | AWAITING_BASELINE → ACTIVE → PAUSED/RETIRED | Verified first baseline under new signed generation; separately authorized pause/retire | Signed lineage and effective interval; exposure under old generations persists under financial ownership |
| **Consumer new-risk opportunity** | UNDECIDED → REVIEWABLE / PRE_DISPATCH_BLOCKED → COMMITTED_ONCE / MISSED | Changed canonical signal plus own mandate and independent account/quote/risk checks; bounded pre-dispatch re-evaluation; irreversible possible-dispatch commit or expiry | One outcome per source signal × financial consumer; never retry potentially dispatched/unknown broker orders |

These are **separate** logical lifecycles; do not make a Cartesian product or use one mutable `ACTIVE`/`GREEN` status for all. The table specifies *contractual boundaries*, not a proposal to add three new services or duplicate journals. In particular, Guardian's existing order statuses/semantic journal remain the protected finance owner; the opportunity lifecycle is **not** a second broker-order state machine. `financial HALT`, broker certainty, source continuity, release activation and economic qualification are orthogonal facts. Source availability or a UI green light cannot clear a financial HALT.

**Transition enforcement invariant:** every attempted transition has a typed predecessor, cause/original evidence and version, applicable signed policy, actor/authority, as-of cutoff, guarded next state, and exactly one owner-local durable effect/rejection. Replays must verify the same legal transition by its *historical* policy version; no implicit transitions by timestamp arithmetic, empty lists, expired process leases, booleans, missing rows, cache updates or service restarts. Illegal transitions are explicit, attributable rejections. A consumer may receive evidence at least once, but each financial effect belongs to one local journal; do **not** claim globally exactly-once cross-database delivery.

**Observed implementation mismatch:** `pm_source_contracts.PositionObservation` already types BASELINE/UNCHANGED/OBSERVED_STATE_CHANGE/DUPLICATE, but the current reducer still accepts a `previous` dict with `baseline_valid` and runs *event-driven* source rules, not the approved five-minute state machine. `prop-production.financial_semantics` has allowed statuses and semantic conservation/HALT checks, but no approved new checkpoint/mandate/opportunity transition reducer yet. None of the future lifecycle labels above is installed or tested by these ADRs.

**Round 5 residual frontier was subsequently resolved by Q21–Q24 below.** Measured source/provider numeric limits and scientific results remain **fact-gathering/proof tasks**, not an invitation to create more readiness flags.

## Owner-approved Round 6 — residual exposure, expiry, reversal and cutover (2026-11-12)

**Q21=A — residual positions survive immutable mandate succession.** The old account-bound mandate generation retains attribution and financial obligations for every position, fill, reservation, pending/UNKNOWN order and risk latch attributable to its effective interval; its retirement prohibits new opening risk but does not delete management of existing exposure. The successor mandate starts in AWAITING_BASELINE with a distinct generation and no copy-current entry. New generation's independently eligible openings can proceed **only when** total actual and reserved account exposure, old-generation residuals, pod attribution and global/pod caps are independently coherent and the new operation cannot duplicate a still-unresolved old effect. A former generation's holdings are never silently relabeled as the successor's, nor counted twice. Same underlying shared source CWSA epoch remains untouched when only a follower mandate changes.

**Q22=A — bounded original-checkpoint opportunity expiry.** Every new-risk opportunity has a durable original source checkpoint ID, first admissible receipt/decision clocks and immutable expiry at the **earlier of** the next five-minute UTC boundary or a separately signed, freshness-bounded deadline. It may be re-evaluated only within that original window while no order could have reached the broker (Q13=B). Expiry is a terminal **MISSED** result, including when the next checkpoint is itself unavailable; a restart, recovered late source packet, changed quote or unchanged target cannot create a fresh opportunity. On boundary equality, expiry is processed before new-boundary admission. Existing residual positions, source-driven reductions at valid future checkpoints, and independently protected risk exits use their own evidence/authority; they do not inherit the expired opening deadline.

**Q23=A — proof-guarded cross-zero reversals, otherwise reduce-only.** Guardian may represent a source-driven reversal as **one** account/instrument net broker order only if the destination venue's native order semantics, allowed quantity/position mode, margin/netting rules, release policy, actual holding, outstanding orders and cross-zero risk all independently prove that a single order can first remove existing exposure and then open only the approved opposite-side exposure without violating attribution or risk. If any part is unknown, admit only independently verifiable **reduce-only** action and record the new opposing exposure as MISSED for that source checkpoint (do not queue an automatic second opening order). Conservatively account for partial reductions, fill/cancel races and UNKNOWN broker responses; protective risk remains independently owned. Do not interpret a leader sign flip as a license to ignore old-generation residuals or the one-shot rule.

**Q24=A — forward-only staged cutover with one financial policy.** Dual old-T0+300 and new-grid source consumers may run **read-only** in parallel for evidence and economic comparison. SHADOW and virtual paper are separately pinned and independently verified first. Any authorized protected account/pod has exactly **one opening-effective signed policy/release generation** at a time; adoption uses an explicit future-effective checkpoint/mandate epoch, authenticated baseline, original evidence continuity, clean companion pins, source/market/account proof, and a distinct authorized Guardian admission. No dual live opening paths, automatic cross-version source replay or implicit promotion from SHADOW. A rollback changes compatible code or moves to an explicitly signed forward successor / DISARMED state; it never rewinds original source journals, orders, signer trust floor, economic receipt versions, financial HALT or pending UNKNOWN obligations. If an older binary cannot understand new durable state, **HALT new risk instead of unsafe rollback**. Existing v1/v2 and deployed T0+300 history retain original version-specific meaning.

**Combined design consequence.** The fully approved Q1–Q24 architecture is two authorities plus one signed relation: common CWSA source continuity/checkpoints, separately signed account-bound Copy Mandate generations, and each existing paper/Guardian finance owner. Explicit owner-local transition tables replace implicit flag/timestamp state; do not create a second Guardian, planner scheduler, broker journal or globally atomic FSM. Operational numeric thresholds and scientific evidence remain measurement/authorization tasks, not unresolved domain decisions. See [the design closure and acceptance map](../CANONICAL-5M-DESIGN-CLOSURE-20261112.md).

## Why this abstraction

The existing source-to-paper path schedules per-observed-transition T+300; `prop-production.v4_timing.V4ShadowProjection` separately schedules market-level T+300 eligibility. These implementations can diverge on local first-known time, coalescing and recovery. One checkpoint-state authority removes the *need for duplicated source timing*, not the need for independent Guardian verification and durable uncertain-broker-outcome recovery.

The alternative rejected for this *new policy* is to keep independent first-transition clocks for each consumer. The existing T+300 system remains a supported historical/current version until deliberately retired through a new contract and reversible release.
